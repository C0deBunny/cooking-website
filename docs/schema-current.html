recipe_images

Gallery images for one recipe. Rewritten wholesale by save_recipe() on every save, like the other two children — even though the wizard sends exactly one row, flagged primary. The many-row shape is what makes a gallery a UI change later rather than a payload change.

Constraints hand-maintained

  • primary key (id)
  • foreign key (recipe_id) references recipes (id) on delete cascade
  • unique (recipe_id, storage_path)
  • unique (recipe_id, sort_order)
  • check (length(trim(storage_path)) > 0)

Indexes hand-maintained

  • recipe_images_one_primary_idx — unique on (recipe_id) where is_primary: unlimited images per recipe, at most one primary

Notes hand-maintained

  • save_recipe() writes this table as of 20260808140818_save_recipe_images.sql — delete-then-insert of the whole set with ordinality, the same treatment steps and ingredients get. That is what retired the collision worry in issue 1 of docs/known-issues.md:13: positions come from array order and the old rows are gone before the new ones land, so the non-deferrable unique (recipe_id, sort_order) never fires. Only a gallery editor that patched rows in place — which nothing does — would still hit it.
  • storage_path holds a path inside the recipe-images bucket, not a URL, so the project id and CDN host stay out of the database. docs/image-storage.md.
  • on delete cascade removes these rows but NOT the files they name — Postgres has no idea the bucket exists. deleteRecipe reads the paths BEFORE the row delete for exactly that reason; docs/image-storage.md:98 explains which way each half-failure has to fall.
  • There is no alt column — dropped in 20260808140817_recipe_images_drop_alt.sql because both placements pass alt="" and a column carrying null forever reads like a bug. Do not add it back for symmetry.
  • ⚠ A row with is_primary false renders nowhere: getRecipes() filters the embed on is_primary, so the file exists, the row exists, and no surface shows either. Nothing raises. Safe today because save_recipe() is only ever handed one image and the wizard always flags it.

Functions

save_recipe(payload: Json) → number

The only write path for a recipe and its children.

Security: security invoker · set search_path = '' · execute revoked from public and anon, granted to authenticated

  • Exists because Supabase JS sends every statement as its own transaction, so a delete-then-insert of children could leave a recipe with no steps.
  • Writes all three children — recipe_steps, recipe_ingredients and recipe_images — as whole sets, taking position from array order via `with ordinality`. Delete-then-insert, which is also why the non-deferrable unique constraints on the ordering columns never fire.
  • Deleting recipe_images rows does not delete the files they name, so replacing a cover through this function orphans the old object. Accepted, and recorded as issue 4 of docs/known-issues.md:104.
  • Extend it by reading another key off the payload, never by adding parameters.

unreferenced_image_paths(paths: string[]) → string[]

Row-level security hand-maintained

Enabled on all four public tables AND on storage.objects — Storage is a second policy surface, and the table model below stops at the table boundary. Two roles either way: visitor (anon) and admin (authenticated), every logged-in account being an admin. anon is granted nothing on storage.objects because rendering never touches it: a public bucket serves object bytes over /object/public/…. The select policy there is required rather than defensive, and this was probed rather than reasoned — storage-api runs the user-facing delete as the caller, with a where clause and `returning`, so with no select policy the delete affects zero rows and still reports success (docs/image-storage.md:119). The recipe-images bucket ROW (public, file_size_limit 2097152, allowed_mime_types {image/webp}, created by 20260808140816_recipe_images_storage.sql) is deliberately absent from the table below: it is data in storage.buckets, so no diff engine sees it and it has to be checked by hand — issue 5 of docs/known-issues.md:138. Full model: docs/permission-model.md; the Storage half: docs/image-storage.md.
