Two layers, both must pass

Table grants are checked separately from policies. select is granted to anon, authenticated; insert/update/delete only to authenticated. RLS then narrows further.

Two roles by design: visitor and admin

Every logged-in account is an admin — there are no normal user accounts. So using (true) is correct, and no table needs a user_id: recipes aren't owned by an account. The trade-off accepted: account creation is the only admission control, so signups stay disabled and accounts are made by hand.

What the schema itself tells us — input for the redesign

  1. The permission model stops at the table boundary — Storage isn't covered. recipe_images.storage_path and recipe_steps.image_path point into a Supabase Storage bucket, and no bucket is defined: config.toml has only the stock commented-out examples, and no migration touches storage.objects. Files get their own separate policies, so "visitors read, admins write" is currently enforced for rows and not at all for the images those rows name.
  2. The ordering uniques are not deferrable. unique (recipe_id, step_number) and unique (recipe_id, sort_order) fire per-statement, so swapping two rows' positions collides mid-update. Reordering needs a temp value, a negative-offset pass, or delete-and-reinsert.
  3. recipe_images.sort_order has no unique constraint — unlike the other two children. Its unique is on (recipe_id, storage_path) instead, so two images can share a position and the gallery order becomes non-deterministic. CLAUDE.md currently describes all three children as unique on their ordering column.
  4. The primary image is a flag, not a reference. A partial unique index caps it at one per recipe, but recipes has no pointer to it — so "recipe + cover image" is always a join plus a where is_primary, and a recipe can legally have images with no primary at all.
  5. Ingredients are free text. name and unit are unconstrained text, so "tbsp" / "tbsp." / "tablespoon" are three different units and nothing can aggregate across recipes. Deliberate — the rejected alternatives are recorded — but it is the wall you hit for shopping lists or "recipes with plantain".
  6. No categorisation and no publish history. No tags, cuisine, or course; published is a single boolean with no published_at, so the public list orders by created_at and un-publishing loses when it went live.
  7. Child rows carry no timestamps. Only recipes has created_at/updated_at, and its updated_at does not move when a step or ingredient changes — an edit to instructions leaves the parent looking untouched.
