Schema redesign — Approach A vs Approach C

Both deliver the same four content features: ingredient groups, prep/cook split, notes, tags. They differ in one decision only — whether steps and ingredients stay as rows or become jsonb inside the recipe row. Everything below follows from that.

Note added 2026-08-08 — historical record. Docker was unavailable when this comparison was written, and several passages below lean on that: the plpgsql function being "untestable without Docker", and db:diff needing Docker so this project has "no drift detection". Docker Desktop has since been installed, so npm run db:diff does detect drift. save_recipe is still only exercised against the linked project, because this project runs no local stack. The comparison and the conclusion it reached are otherwise unaffected.
The trade, in one line: A keeps the database validating your data and db:types typing it, and pays for that with a SQL function you have to write. C makes the save trivially atomic and groups free, and pays for that by making the database blind to what's inside the blob.

2 · What happens when you hit Save

the reason this choice exists at all — each Supabase request is its own transaction
AOne RPC, one transaction
1zod validates the form
2supabase.rpc('save_recipe', payload)
inside the function — one transaction
upsert recipes
delete ingredients, steps, recipe_tags
insert ingredients  idx → sort_order
insert steps        idx → step_number
insert recipe_tags
3commit — or nothing happened at all
✓ 1 round trip · all-or-nothing · a failed insert leaves the old recipe fully intact

Cost: you write and maintain a plpgsql function, and with no Docker you can only exercise it against the real project through the app.

COne update — plus tags
1zod validates the form
request 1 — atomic by definition
update recipes set
  ingredients = '[…]'::jsonb,
  steps       = '[…]'::jsonb,
  title = …, prep_minutes = …
request 2 — separate transaction
delete from recipe_tags where …
insert into recipe_tags …
~ The recipe body is bulletproof. Tags are not — they're still two requests, so a failure between them loses the tags.

If tags are deferred, C becomes a genuine single statement with no function to write at all — that's its strongest form.

4 · What the database will refuse to store

zod guards your form; this guards everything else — Table Editor, scripts, a future API
ARefused at the database
✓ amount check (amount > 0)
✓ name   check (length(trim(name)) > 0)
✓ unique (recipe_id, sort_order)
✓ step_number check (> 0)
✓ recipe_id references recipes

A blank ingredient name or a negative amount is rejected no matter what wrote it.

✓ Constraints hold for every writer, not just the form
CNothing inside the blob
// all of this is a legal recipes row:
ingredients = '[{"name": "", "amount": -5},
                {"nmae": "rijst"},
                "not even an object"]'

✕ no check on any field
✕ no uniqueness on position
✕ zod is the only line of defence

Recoverable with a check (jsonb_typeof(…)) or a validation trigger — but that's hand-written SQL, which erodes the "no function to write" advantage.

✕ One bad script or Table Editor edit and the detail page renders garbage

6 · The thing that will actually bite you

not the theoretical objection — the one you'll hit in month three
ADebugging SQL blind

You write save_recipe, push it, and it fails on a real submit with a message from inside plpgsql. No Docker means no local shadow database, so the loop is: edit, db:push, retry through the form.

Why it's survivable: it's one function, written once, and it stops changing. The pain is front-loaded into the build, not spread across every future recipe.

CSilent shape drift

In month three you rename a key — amount → quantity. New recipes save fine. The twelve existing rows keep amount forever. No migration touches them, no type error fires, and the detail page renders blank amounts for old recipes only.

Why it's worse here specifically: this project already has no drift detection — db:diff needs Docker. A blob whose shape lives only in your head compounds a weakness you already have.

7 · Pick on this basis

both are defensible — they optimise for different things

A  Choose if…

  • You want the database to stay the thing that guarantees your data is sane, not the form.
  • You value npm run typecheck catching a schema change across every reader — the payoff the project was built around.
  • Ingredient search or "what can I cook with X" is plausible later.
  • Writing one plpgsql function is an acceptable one-time cost.

C  Choose if…

  • You want the smallest possible amount of moving parts, now, and no SQL beyond migrations.
  • A recipe is a document you always read and write whole, and you're happy for zod to be the only validator.
  • Deeply nested groups matter more than queryable ingredients.
  • You'd rather defer tags and keep the save to one literal statement.
