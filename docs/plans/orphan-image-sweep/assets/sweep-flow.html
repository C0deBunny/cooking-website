The orphan image sweep

Fires after every successful saveRecipe and deleteRecipe, inside after(), so the owner never waits for it. Four independent filters stand between “every object in the bucket” and “files this run is allowed to delete” — the numbers below are one plausible run.

What the cap is actually for

Healthy run

Step 4 answers correctly. The bucket gains a handful of strays a year and the hook fires on every write, so the orphan list is essentially always 0–3.

candidates past the floor39
step 4 says unreferenced3
cap applies?no — 3 < 25
deleted3
3 42 live files untouched

the cap is never felt

In normal operation the cap does nothing at all. That is the point — it only ever engages when the sweep is already wrong.

Broken run

Step 4 answers wrongly — a narrowed RLS policy, a new image column nobody added to the anti-join, a bad migration. It now reports live files as unreferenced.

candidates past the floor39
step 4 says unreferenced39 ← wrong
cap applies?yes — sliced to 25
deleted25
25 destroyed 20 survive

without the cap: all 39 gone in one save, nothing left to diagnose from

Damage is bounded and the survivors are the evidence. Hitting the cap is therefore a signal in its own right — a correct sweep can’t reach 25 — so it should log loudly.

Why the first run muddies that signal

since 2026-08-08
Nothing collects orphans
Eager upload has been leaking files from abandoned tabs and failed removes since the recipe-images work shipped. That backlog is sitting in the bucket right now, and nobody has counted it.
first deploy · first save
The sweep meets the whole backlog at once
Every one of those files is past the 7-day floor and genuinely unreferenced. If the backlog is 30-odd, step 4 correctly returns 30-odd, and the cap engages — for an entirely benign reason.
the problem
“Cap hit” now means two opposite things
The alarm that was meant to shout “step 4 is wrong, live files are being destroyed” fires identically for “the backlog was bigger than 25”. The one time it goes off, you can’t read it.
after a few saves
Steady state, alarm meaningful again
Backlog drains 25 per write. From then on any cap hit is unambiguous.
The cheap fix: count the backlog by hand before deploying — select count(*) from storage.objects where bucket_id = 'recipe-images' against the referenced counts. Then the first run has an expected number, and the cap only surprises you if reality disagrees with it. No code, no second deploy.
